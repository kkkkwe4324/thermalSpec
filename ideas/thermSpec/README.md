# thermSpec：信道与热状态感知的跨设备投机解码

## 我们在研究什么

手机运行一个独立的小草稿模型，Jetson Orin 运行大目标模型。手机提出 K 个候选 token，Orin 验证后提交有效输出。一次请求的端到端时间同时取决于手机计算、手机与 Orin 间的通信、目标验证和接受率。手机持续运行会升温，系统可能限制实际 CPU 频率；信道 RTT 或带宽变化又会改变多提几个候选 token 是否划算。

核心问题是：**能否同时观察信道状态与手机热状态，联合选择手机 CPU 频率上限和投机长度 K，改善持续运行时的端到端性能？** 本轮草稿在手机 CPU 上执行，因此“DVFS”具体指三簇 CPU 上限请求；系统温控仍可能覆盖请求。Orin 运行模式固定。当前优化指标是解码阶段端到端耗时除以最终有效 token 数（摊销 TPOT），也记录分段耗时和 target-only 参考。没有可信功率数据前不报告节能结论。

这是研究假设。此前短测验证了手机草稿与 Orin 目标的 greedy 输出一致，但投机路径仍比 target-only 慢，通信/服务请求开销是明显瓶颈。正式实验口径现改为 [WildChat 真实用户提示词与分布保持的投机采样](experiments/WORKLOAD_AND_SAMPLING.md)；完整目标验证链路尚待接入。先把真实持续负载和数据采集跑通，再决定是否存在值得控制的热退化与联合选择收益。

## 相关论文如何连接

| 论文 | 已知相关点 | 本项目要核查的区别 |
|---|---|---|
| [EarDVFS, ICCAD 2025](https://doi.org/10.1109/ICCAD66269.2025.11240765) | 移动设备热限频和主动设置上限 | 它没有跨设备投机解码及 K 决策。 |
| [PELM, SenSys 2026](https://arxiv.org/abs/2609.09662) | Orin 上联合 DVFS 与自投机相关配置 | 本项目是手机独立草稿＋Orin 目标，并考虑跨设备信道。 |
| [BanditSpec, ICML 2025](https://proceedings.mlr.press/v267/hou25h.html) | 普通投机的在线长度选择 | 本项目还要看热状态与手机 DVFS 的耦合；固定 K 损失需要实测。 |
| [FlexSpec, IEEE TMC 2026](https://doi.org/10.1109/TMC.2026.3683574) | 端云信道感知 K 选择，是直接相关工作 | 需核实正式版对热状态和频率控制的具体覆盖范围，不能预设其没有。 |
| [SpecDec++, COLM 2025](https://openreview.net/pdf/20e04fa6a4fd4676e6c928f26603189768563b4a.pdf) | 根据接受概率停止草稿 | 需要与通信、温度引起的端到端开销变化区分。 |

当前只据已阅读的论文部分及检索记录定位关系；正式创新性判断仍需复核全文和相应公开实现。

## 实验路线与当前阶段

1. [动机实验 1](MOTIVATION_EXPERIMENTS.md)：固定 K，持续推理，观察温度、实际频率和 TPOT；比较高上限与适中上限。
2. 动机实验 2：好/差信道 × 三种初始热状态，扫描 K=1–8，量化固定 K 的损失。
3. 动机实验 3：好/差信道 × 冷/热状态，扫描三档 CPU 上限 × K，判断联合选择的实际空间。
4. 实验 4 留待方法定义后再设计。

代码按[框架设计](EXPERIMENT_FRAMEWORK_DESIGN.md)区分论文复现、单次运行、矩阵调度和每项实验自己的分析脚本。当前已经有手机草稿的真实短运行闭环；**还没有完成 Orin 验证接入及正式实验 1**。设备部署背景见 [SETUP](SETUP.md)。
